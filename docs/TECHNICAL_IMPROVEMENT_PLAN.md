## 3. 对原计划的调整

保留执行记录、可管理记忆、任务恢复和上下文预算的方向，但调整顺序：

1. 在新增长期记忆前，先修复用户可见写入的可靠性，并建立隔离预览与真机验收流程。
2. 先完成已有 Agent/RAG 的可重复效果证据，再增加新的 Agent 架构。
3. 先用当前已有七天数据支持只读周总结；不要为一个短请求立即引入持久任务调度器。
4. 先测量上下文长度与质量，再决定是否需要摘要、向量记忆、重排或流程包。
5. 记忆与健康数据管理上线前，补齐删除、保留期限和隐私说明。

“剩下只需要用户提供账号或密钥”不准确：普通写入层、评估隔离与覆盖、数据集/食物库整理、记忆与恢复机制都有工程工作。

## 4. 第一优先级：可靠写入与可测试发布

### 4.1 普通写入可靠性

已有 Agent RPC 和部分食物编辑路径可靠性较好，不需要重写。逐一检查普通 meal/workout/favorite/knowledge 的创建、修改和删除及其调用页面。

- 改为可等待的 Promise 和明确成功/失败结果。
- 失败时恢复界面或重新读取；显示可操作错误，不只 console.error。
- 创建重试沿用稳定 ID；验证重复 ID 是同一内容，不能用盲目覆盖实现“去重”。
- 关键写入得到确认前不离开页面；删除有确认或可靠 Undo。
- 防止旧的读取结果覆盖较新的成功写入。

验收：新增/修改/删除失败、超时后重试、连续点击、旧刷新晚到均有确定性测试，刷新后的数据库状态与界面一致。只补真实缺陷路径，不用重复测试堆数量。

### 4.2 隔离测试环境与 iPhone 留白

- 准备 staging 配置说明和安全种子数据；创建独立 Supabase 项目并配置 Vercel Preview。
- 确认 Preview 请求和写入实际指向 staging，配置稳定测试 URL 和认证回调。
- 在真实 iPhone 主屏幕 App 中复现：启动、唤起键盘、关闭键盘、页面切换、旋转与恢复前台。
- 根据复现证据修复 viewport/safe-area；验收启动无留白、键盘关闭无残留、底部导航不遮挡内容。

本地工程可以先做；账号资源配置和真实 iPhone 验收需要用户或可用的账号/设备访问。不要把“回退了错误修复”标为“原问题已解决”。

## 5. 第二优先级：运行记录与真实评估证据

### 5.1 最小执行记录

先延用已有 requestId 和 actionId。为请求内的模型、检索和确认步骤增加关联与耗时，不立即建设完整 task 表。

- 记录端点、步骤类别、结果、错误类别、耗时、模型/提示词/检索版本、token 和估算成本。
- 明确区分模型请求结束、提案等待确认、写入成功和刷新失败。
- action receipt 与遥测记录分开；默认不记录原始对话、图片、健康数值或密钥。
- 明确保留期限、访问权限和删除方式；回放使用模拟工具，不重新写入。

验收：一条失败请求可定位到检索、模型、参数校验、数据库或刷新阶段；取消和超时有终态；检查日志不包含敏感内容。

### 5.2 先修正评估可复现性，再运行实验

- 让所有真实评估模式（包括单独 `--suite tools`）显式限定评估数据库或只读模拟检索，不能依赖进程里恰好不存在生产配置。当前环境替换在 retrieval 分支内，tools-only 需要单独处理。
- 清理并核验 catalog 的来源、品牌、做法和单位；`legacy-unverified` 只是标记，不是质量证明。
- 为实际被查询的数据库 catalog 生成版本/指纹；当前本地 `foods.json` hash 不能证明远程数据集相同。
- 明确 baseline：当前 vector 策略仍使用新元数据/单位过滤；若要声称“旧版对新版”，必须固定真正的旧策略，否则应写成“相同过滤条件下 vector 与 hybrid 的消融比较”。
- 分离开发集与冻结验收集；现有 20 条样本不能自动叫作独立 held-out 集。
- 选择有效的三个模型配置和核验价格，均运行同一完整用例集；当前示例含占位模型、空价格。
- 为每个配置分配足够用例预算，避免顺序执行耗尽全局预算后只完成第一个配置。缺失结果必须是 inconclusive。
- 明确区分实测 token 成本、embedding 预留预算和账单金额；当前总成本停止机制不是绝对不超支的硬上限。

验收：报告包含代码、模型、提示词、scorer、数据集和实际 catalog 版本；同一基准能重复运行；错误接受、拒绝匹配和基础设施失败分开统计。

## 6. 第三优先级：最小可管理记忆

复用现有业务记录和 knowledge；不把餐食、训练、体重复制成一份长期记忆，也不把现有 knowledge 冒充完整记忆系统。

首版只做用户明确确认的稳定偏好与有期限条件：如“不喜欢香菜”“使用公制”“本周出差”。目标优先读取已有结构化 profile。健康限制只记录明确声明并确认的信息，不从照片推断。

建议最小字段：id、user_id、category、value、status、version、source reference、created_at、updated_at、expires_at。需要历史替换时再引入 supersedes 关系，避免无目的保存全部原文。

- 候选提案不进入有效上下文；确认后才生效。
- 提供查看、修改、删除、关闭记忆入口。
- 使用版本条件更新，冲突明确返回；有效用户/状态/期限在数据库查询层过滤。
- 初期采用结构化选择，不默认增加向量索引。
- 删除后缓存失效，避免历史对话再次自动提取恢复；落实完整账号数据删除与导出范围。

验收：跨用户零泄漏、未确认不召回、修改只用新值、过期不注入、删除不复活；比较无记忆与结构化记忆的偏好遵循和 token。只有已具备合规历史存储时才增加“完整历史”比较组。

## 7. 第四优先级：按需增加任务恢复

先实现只读场景：“总结本周餐食与训练并草拟下周建议”，利用已有七天上下文。结构化总量由代码计算，模型负责解释；任何保存仍走确认提案。

只有实际出现跨请求、长时执行或用户离开后继续的需求，才加入 task_id、step_id 和持久任务状态。

届时必须补齐：

- 状态转换、步骤依赖、领取租约与原子更新，避免多个执行器重复领取。
- 时长、步骤数、调用数、token/成本预算及明确终态。
- 服务端提案版本、过期与取消状态；确认绑定准确内容/版本。
- 崩溃恢复前校验用户权限、确认状态与数据版本；查询 receipt 后再决定是否写入。
- 取消只停止未完成步骤，已提交修改需要单独受控撤销。

当前取消是页面交互状态，数据库 RPC 校验的是调用者与 payload，没有持久提案取消/版本/过期记录。现有内容冲突检测不能替代这些机制。对于跨会话保存的确认入口，必须增加服务端约束后才能声称“旧确认无法执行”。

验收：进程在写入前/后退出、重复领取、旧版本确认、取消后恢复、部分失败都可确定结果。跨服务操作单独设计补偿，不承诺统一自动回滚。

## 8. 第五优先级：基于测量优化上下文和检索

先统计当前上下文构成、token、延迟和质量。已有行数/消息长度限制不等于合理的 token 分配；例如 knowledge 当前最多读取 20 条，仍可能产生较大上下文。

- 为系统规则、请求、相关知识、最近对话和工具结果分配预算。
- 优先选择相关知识并对工具结果做结构化摘要；保留来源引用。
- 精确数值、单位、确认内容与写入状态从结构化数据获取，不能依赖自由文本摘要重建。
- 摘要与检索内容始终是数据，不能改变权限或工具策略。
- 有错误分析依据后再比较重排；只有流程数量/上下文开销明显增长后才尝试按需加载流程包。

验收：同模型、同任务比较成功率、遗漏率、token、P50/P95 延迟和估算成本。关键限制或确认状态丢失必须单独判失败，不能被平均分掩盖。
